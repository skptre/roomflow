## Decisions (do not relitigate)

- **D1 — Data source:** Shopify public product feeds from the verified store list, harvested by a script into a committed, dated snapshot. Every offer keeps `retrievedAt`, merchant, and the variant URL. Snapshot, not live-only, so the demo works offline and reproducibly. A live **refresh** re-reads one product's price/availability through our server.
- **D2 — Identity:** `Product` = Shopify product (`shop:<store>:<productId>`), `Variant` = Shopify variant (`…:<variantId>`), `Offer` = that variant's price at `retrievedAt` from that store. `isSample: false`. URL = variant URL. Never invent a price: unparseable → `null`.
- **D3 — 3D representation:** new `AssetRef` kind **`recipe`**: `{ kind: 'recipe', recipeId, colors }` where the recipe (per product) names a **family**, its **block choices**, bounded **params**, and maps variant options → material-slot colors. The browser builds geometry from blocks. Existing `parametric`/`glb`/`placeholder` kinds keep working (sample catalog stays only as a test fixture).
- **D4 — Dimensions are authoritative from the merchant.** Recipe params only shape internal proportions (arm width fraction, leg height…). Unknown dimensions → category typical, `source: 'estimated'`, and fit conclusions stay disabled as today. Assembled dimensions only; ignore shipping/box dimensions.
- **D5 — Coloring is the #1 visual requirement.** Each material slot gets an sRGB hex. Source order: (1) Gemini reading the variant image + option name, (2) curated color-name lexicon (`Walnut`, `Oak`, `Heather Charcoal`, `Navy`, `Brass`…), (3) product image dominant color. The lexicon also sanity-checks Gemini (hue family must agree for common names). Colors are rendered with correct color management (three.js `Color` from sRGB hex; NeutralToneMapping already on).
- **D6 — No surface textures.** Flat materials per kind (`fabric`, `leather`, `wood`, `metal`, `ceramic`, `glass`, `stone`, `plant`, `paper`) with fixed roughness/metalness. **Only artwork canvases and rug tops use the product's own image** (via Shopify CDN `&width=1024`), because that image is the product. If an image fails to load → flat dominant colors (never a broken texture).
- **D7 — No customize panel.** Variant choice (color swatches, sizes) lives on the product card in the catalog. Hover = preview in room, click = place/replace (existing preview/commit/undo pipeline). "Try a look" draws from the real catalog.
- **D8 — AI boundary:** AI (Gemini) only interprets **public product data** (title, options, description text, public product images fetched by *our server* from the store CDN) into a validated recipe. It never sees the room, never writes code, never sets prices or overrides merchant dimensions. Personal photos (found items) are processed locally; sending a crop to AI requires explicit per-request consent with a cost quote.
- **D9 — Model selection:** server calls `GET https://generativelanguage.googleapis.com/v1beta/models` with the key, picks the configured `GEMINI_MODEL` if present, else the cheapest available `*flash-lite*` that supports `generateContent`; logs the choice. Pin the chosen ID in the ledger and the recipe (`generator: { model, schemaVersion }`).
- **D10 — Server:** a Vite plugin (`configureServer` / `configurePreviewServer`) exposing `/api/*` inside the dev/preview server — no second process, no new framework. Secrets from `web/.env.local` via `loadEnv(mode, cwd, '')` (never `VITE_`-prefixed). Scripts run with `tsx` (single new devDependency) so they share the same TypeScript modules.
- **D11 — Privacy enforcement:** CSP header on the app: `connect-src 'self' ws: wss:` and `img-src 'self' data: blob: https://cdn.shopify.com`. The browser therefore cannot send data anywhere but our own server. All outbound AI/store calls happen server-side through one `egress` gateway with an allowlist.
- **D12 — Spending controls:** server-side ledger (`web/.data/ledger.jsonl`, gitignored) records every AI call: purpose, model, input class (`public-product` | `user-photo`), tokens (from `usageMetadata`), cost in micro-USD from a versioned rate card, status. Before each call **reserve** a worst-case cost; refuse if it exceeds the remaining daily cap (`AI_DAILY_CAP_USD`, default 2.00) or per-call cap. Reconcile with actual usage after. Recipes are cached on disk by `(productId, evidenceHash, schemaVersion, model)` so a product is never paid for twice.
- **D13 — Tool selection is explicit and deterministic**, cheapest first: cached recipe → rules-only recipe (keywords + lexicon, free) → Gemini recipe (paid, public data) → category default family → placeholder box. Each object records which tier produced it and the evidence states ("dimensions: merchant · colors: from photo · shape: matched family 'sofa/track-arm'"). No invented "93% accurate" scores.

```
      shopify.ts               # feed types (zod), fetch helpers (injected fetch), pagination, polite rate limit
      normalize.ts             # Shopify product → Product/Variant/Offer drafts + evidence
      money.ts                 # "4497.00" → 449700 (string math), cents ints

      colors.ts                # color-name lexicon, hue-family check, dominant-color helpers
    blocks/                    # the building-block library (pure geometry data, no React)
      kit.ts                   # geometry primitives: roundedBox, cushion, lathe, extrudeProfile, tube, taperedLeg…
      materials.ts             # flat material kinds (roughness/metalness), slot → Material cache
      families/*.ts            # sofa, chair, bed, table, storage, lamp, plant, vase, rug, art, mirror, curtain, pillow, throw
      recipe.ts                # Recipe zod schema + validateRecipe (enums, ranges, slots, colors) + defaults per family
      build.ts                 # (recipe, dimensions, colors) → { geometry per material slot } (merged, cached)
    scene/RecipeMesh.tsx       # renders build.ts output; one draw call per material slot
    catalog/                   # runtime catalog: loads snapshot, indexes, search, variant groups
    server/                    # Vite-plugin API (runs in Node): egress gateway, ledger, gemini client, routes
  scripts/
    harvest.ts                 # stores → web/public/catalog/snapshot.json (+ report)
    recipes.ts                 # snapshot → web/public/catalog/recipes.json (rules tier, then Gemini tier under cap)
    lineup.ts                  # headless screenshots: product photo vs rendered block model, per family (QA)
  public/catalog/              # committed snapshot + recipes (dated)
  .data/                       # gitignored: ledger, recipe cache, raw feeds
```

**Recipe (schemaVersion 1) — shape, not final code:**
```ts
{ id, productId, family: 'sofa' | 'chair' | 'bed' | …,
  blocks: { arm: 'track' | 'rolled' | 'slope' | 'none', base: 'tapered-legs' | 'block-legs' | 'plinth' | 'hairpin', … },  // enums per family
  params: { seatCount: 3, backHeightFrac: 0.45, legHeightM: 0.12, … },   // bounded per family; meters for real-size details
  slots: ['upholstery', 'legs'],                                          // material slots this family exposes
  materialKind: { upholstery: 'fabric', legs: 'wood' },
  optionColors: { 'Fabric': { slot: 'upholstery', values: { 'Heather Charcoal - …': '#4a4b4d', … } },
                  'Leg Finish': { slot: 'legs', values: { 'Walnut - Wood': '#5b3a24', … } } },
  defaultColors: { upholstery: '#…', legs: '#…' },
  image?: { slot: 'canvas' | 'rugTop', url },                              // art/rugs only (D6)
  tier: 'rules' | 'gemini', generator: { model?, schemaVersion: 1 }, evidence: { colors: 'photo'|'name'|'default', shape: 'matched'|'default' },
  unmatched: string[] }                                                    // features the blocks can't express → drives new blocks
```
Variant colors = `defaultColors` overridden by each of the variant's option values found in `optionColors`.
